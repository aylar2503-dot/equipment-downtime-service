# Мониторинг простоев оборудования — версия 2.0

Учебный проект №16. REST API принимает статусы станков, регистрирует простои в SQLite, отсекает повторные сообщения `STOPPED`, сохраняет сведения об уведомлениях VK и задачах Jira.

## Логика работы

1. `POST /api/events` принимает `machine_id`, `status=RUNNING|STOPPED`, необязательное `stopped_at` (ISO 8601 с часовым поясом).
2. SQLite в одной транзакции сохраняет событие и при **новой** остановке — начало простоя, запись о будущем VK-уведомлении и запись о будущем Jira-инциденте.
3. Только после сохранения данных сервис вызывает Jira и VK. Сбои внешних сервисов не уничтожают уже полученное событие.
4. Повторный `STOPPED` у уже остановленного станка не создаёт новый простой, Jira-задачу или VK-сообщение.
5. Первый `RUNNING` после простоя закрывает интервал и вычисляет его длительность.
6. Следующий `STOPPED` после `RUNNING` создаёт новый независимый инцидент.

## Файлы

- `main.py` — FastAPI, SQLite, обработка событий.
- `jira_integration.py` — существующий, **не заменяемый** модуль Jira (реальное создание задачи уже подтверждено SCRUM-5).
- `vk_notifier.py` — существующий модуль отправки VK.
- `dashboard.html` — существующая панель.
- `.env` — локальные секреты. **Не отправлять в GitHub и не пересылать.**
- `tests/` — проверки REST API, фильтрации событий и обработки сбоев интеграций на изолированной базе.
- `requirements-project.txt` — минимальные библиотеки для воспроизводимого окружения.

## Настройки

В локальном `.env`:

```env
JIRA_MODE=demo
JIRA_URL=https://YOUR-SITE.atlassian.net
JIRA_USER=your-account-email@example.com
JIRA_API_TOKEN=YOUR_PRIVATE_TOKEN
JIRA_PROJECT_KEY=SCRUM
```

В этом файле не нужно указывать свои секреты вместо примеров: это только инструкция. **Используйте реальный токен исключительно в локальном `.env`.** Его настоящий текст в документации, скриншоты и Git не включать.

* `JIRA_MODE=demo` — не создаёт настоящих задач, полезно для автоматических проверок.
* `JIRA_MODE=live` — создаёт **настоящие** задачи в Jira, использовать только осознанно.
* `SERVICE_API_KEY` (необязательно) — при заданном значении каждый POST-запрос должен иметь заголовок `X-API-Key`. Для сети/публикации рекомендуется обязательно установить ключ и отдельно защитить доступ к GET/панели сетевыми средствами.
* `EQUIPMENT_DB_PATH` (необязательно) — путь к другой SQLite базе. Если переменная не задана, используется `equipment.db` рядом с `main.py`.

## Запуск на Lubuntu / Ubuntu

В терминале VS Code, в корне `equipment-downtime-service` с активной `.venv`:

```bash
python -m pip install -r requirements-project.txt
python -m pytest -q
python -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

Рабочие адреса (только на своём компьютере):

- Сервис: `http://127.0.0.1:8000/`
- API-документация: `http://127.0.0.1:8000/docs`
- Панель: `http://127.0.0.1:8000/dashboard`
- Проверка БД: `http://127.0.0.1:8000/health`
- События: `http://127.0.0.1:8000/api/events`
- Состояния станков: `http://127.0.0.1:8000/api/machines`
- Простои: `http://127.0.0.1:8000/api/downtimes`
- Уведомления: `http://127.0.0.1:8000/api/notifications`
- Инциденты Jira: `http://127.0.0.1:8000/api/incidents`

Через `/docs` можно нажать на **POST /api/events → Try it out**, отправить:

```json
{"machine_id": "CNC-DEMO-01", "status": "STOPPED", "stopped_at": ""}
```

Если `JIRA_MODE=demo`, новая реальная задача в Jira **не** появится. После проверки можно отправить `RUNNING` для того же станка. Повторный `STOPPED` до `RUNNING` не создаст второй инцидент.

## Сценарий защиты на 3–5 минут

Покажите цепочку от REST-запроса до двух записей о доставке. Для демонстрации используется новая временная база, штатный демо-режим Jira и имитация успешного ответа VK.

В корне проекта установите зависимости и запустите демонстрационный экземпляр в первом терминале:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-project.txt
.venv/bin/python -m pytest -q

demo_dir=$(mktemp -d)
EQUIPMENT_DB_PATH="$demo_dir/equipment.db" JIRA_MODE=demo SERVICE_API_KEY= \
  .venv/bin/python - <<'PY'
import uvicorn
import main

main.send_vk_message = lambda message, random_id: 1
uvicorn.run(main.app, host="127.0.0.1", port=8001)
PY
```

Откройте [панель](http://127.0.0.1:8001/dashboard) и [Swagger UI](http://127.0.0.1:8001/docs). Во втором терминале определите функцию для отправки события:

```bash
event() {
  curl -fsS http://127.0.0.1:8001/api/events \
    -H 'Content-Type: application/json' \
    --data "{\"machine_id\":\"CNC-DEFENSE\",\"status\":\"$1\"}"
  printf '\n'
}
```

Выполняйте команды по одной. Между первой остановкой и возобновлением работы дайте панели обновиться хотя бы раз.

| Команда | Ожидаемый результат |
| --- | --- |
| `event RUNNING` | HTTP 200, `notification_needed: false`, обе доставки имеют статус `not_required`. |
| `event STOPPED` | HTTP 200, `notification_needed: true`, Jira — `demo` с ключом `DEMO-2`, VK — `sent`. В панели появился один активный простой. |
| `event STOPPED` | HTTP 200, `notification_needed: false`, обе доставки имеют статус `not_required`. В панели по-прежнему один простой. |
| `event RUNNING` | HTTP 200, простой закрыт, `duration_seconds` содержит итоговую длительность. |
| `event STOPPED` | HTTP 200, начался второй простой, Jira вернула `DEMO-5`, имитация VK снова вернула успех. |

В таблице «Простои оборудования» покажите закрытый и активный интервалы. Для сверки через API откройте `GET /api/downtimes`, `GET /api/incidents` и `GET /api/notifications`. После пяти запросов каждый из этих маршрутов покажет по две записи. Ключи `DEMO-*` и статус VK `sent` в этом запуске подтверждают работу сценария с тестовыми интеграциями. Завершите демонстрационный сервер сочетанием Ctrl+C.

## Тестирование без внешних отправок

`python -m pytest -q` запускает весь набор проверок. Тесты используют SQLite во временных папках и подмены Jira и VK, поэтому локальная `equipment.db` и внешние системы остаются вне тестового запуска.

Тесты охватывают повторные статусы, несколько станков, длительность простоя, время от оборудования, отказ VK, неопределённый ответ Jira, защиту от двойной отправки, повтор VK по тому же `random_id`, REST-маршруты, ошибочную валидацию и опциональный API-ключ.

## Обработка ошибок Jira

После записи в SQLite перед запросом в Jira инцидент переходит в `sending`. Если Jira вернула подтверждение — `created` (или `demo`). При таймауте/неясной ошибке статус становится `uncertain`: **нельзя просто повторить запрос**, поскольку Jira могла уже создать задачу. Если процесс завершился во время отправки, сохранится `sending`, и также нужна проверка Jira. Эти состояния видны через `GET /api/incidents`. У сервиса сознательно нет автоматической повторной отправки неопределённых Jira-запросов.

Чтобы разрешить `uncertain` или `sending`, необходимо найти задачу по станку, времени и ID события в Jira и сверить её с SQLite. Для устранения таких случаев в будущем можно добавить отдельный защищённый административный workflow с подтверждением или внешним уникальным ID. Сервис **не обеспечивает распределённую exactly-once доставку** между SQLite и Jira; это ограничение REST-интеграции без общей транзакции.

VK-повторы выполняются через `POST /api/notifications/retry` для `pending`/`failed`. Сохраняется исходный `random_id`, чтобы VK мог отсеять дубликат. Для восстановления после полного падения процесса во время отправки может понадобиться ручная проверка записи `sending` (в текущем коде исходная VK-функция не изменялась).

## Безопасность Git

Файл `.gitignore` дополняется правилами для локальных баз `.db`, `.env`, кэша Python, резервных копий и другого учебного репозитория внутри проекта. **Важно:** `.gitignore` не удаляет из истории файлы, которые уже были добавлены в Git раньше. Проверяй вывод `git status` перед индексированием. Не используй `git add .`, пока в проекте лежит папка `Data-Science-For-Beginners-from-scratch-course` или секретные файлы.

Изменения в GitHub не отправляются автоматически установщиком. После тестов отдельно проверяют `git status --short` и добавляют только необходимые файлы.
